01 · Pipeline

工作流全景End-to-end pipeline

从一个平铺 9 个文件的本地文件夹，到可交付资料包，共 9 个阶段。红圈 = 该阶段遇到并解决了技术卡点。

  • 资产盘点与格式解析
    列全量文件 → 精读 2 份报告 → 识别出这不是 9 份独立资料，而是同一条数据链的 5 个迭代版本 + 3 份产出报告 + 1 份规则源文件。这一步决定了后面「归类」和「只留最终版」的成立。
    读 Excel 的通道不支持非系统盘 .wps 是 OLE2 二进制
  • 数据核验与口径确立
    对主表 74 条逐行实算，再把结果与两份已有报告逐项对照 —— 发现既有报告的全部均价与极值都与源表对不上。随即确立双口径并写死到生成脚本里。
    既有报告数字整体失真 双口径确立
  • 首版交付
    静态 HTML 报表（手写 SVG 图表 + 原生 JS 搜索/筛选/排序）+ 整理版 Excel（4 sheet）。核心约束：单文件、零外部依赖、断网可看。
  • 文件夹物理归置
    全量备份 → 建 5 目录 → 分 3 批移动 → 字节级校验 → 写 README。9/9 文件字节数与备份完全一致。
    零删除 / 零改名 / 零覆盖
  • 设计改版与口径统一
    保留用户提供的 CSS/JS 设计层，正文数据全部重新生成。核对时发现该设计版的图表计数（74 口径）与正文百分比（65 口径）自相矛盾，同步修正 5 处。
    口径混用修正 5 处
  • 版式微调
    排行榜两表并排时列宽被压到 40px，文字全折行。改为上下堆叠，并补上作用域受限的防回归 CSS。
  • 外部调研
    按贴合度调研 GitHub 同题材项目。4 个候选里有 1 个压根不存在，逐个核实后才给结论。
    1/4 候选是 404
  • 交互看板
    内联 Chart.js 4.4.4 实现四维联动筛选。准备数据集时做两表交叉验证，又发现「区域划分」列 5 处冲突。
    内联后数据全空 两表区域标注冲突
  • 定稿与交付物净化
    报告收尾时复核三个 HTML 交付物，查出预览器把 data-page-node-id 属性回写进了文件 —— 静态报表被注入 1,872 处、看板 493 处，体积近乎翻倍。统一剥离后重新同步，并补齐打印样式与阅读辅助（进度条 / 返回顶部 / 导航高亮）。
    预览器回写污染交付物 三个 HTML 全部净化

03 · Pitfalls

踩坑与解法Pitfalls & solutions

这一节是整份报告里最可复用的部分 —— 11 个坑（10 条本次实测 + 1 条历史经验复用），每个都记了「表现」和「解法」，下次遇到直接照做。

#坑表现解法
1 读 Excel 的子代理不支持非系统盘 F:\ / F:/ / /F:/ 三种写法全部失败，报 INVALID_LOCAL_PATH 非 C 盘的 xlsx 直接用 openpyxl 读，不走子代理通道
2 .wps 是 OLE2 二进制 当文本读全是乱码，看不到区域划分规则 olefile 打开 → 读 WordDocument 流 → utf-16le 解码 → 正则捞中文
3 Chart.js 内联后页面数据全空 CSS 完全正常，KPI 和图表全空白 —— 极易误判成渲染问题 UMD 文件以多行注释块开头，按行截断只剩孤立 */ → 整段 script 语法错误。改为按 */ 定位切割
4 多版本数据文件的标注冲突 两张主表 5 条记录区域不一致，不知该信哪个 做内部一致性检查：同一实体是否被拆到多个类目。自相矛盾的那份出局
5 统计口径混用 图表画 46 套、正文写 39 套，同一段话自己打自己 口径写进图注与脚注；生成脚本里两个口径分别命名（N / NS），正文数字全部用变量，杜绝手写
6 CSS nowrap 加得太宽 排行表不折行了，但说明/备注长文本列横向溢出 收窄作用域：用具体类（td.num / table.rk）替代 tbody td，再对个别列 white-space:normal 放行
7 无头截图截的是视口 --screenshot 配 #anchor 定位不到目标区块（smooth scroll 干扰） 生成临时 HTML，在 </style> 前插 display:none 隐藏无关 section；中文路径需 percent-encode
8 转述的外部资源不可靠 4 个候选仓库里 1 个是 404 任何外部资源（仓库 / 链接 / 数据）先核实存在性，再谈内容
9 GitHub 搜索 API 未登录限流 连续查询后返回 403 限流 10 次 / 分钟，超了读响应头等重置；查询之间加间隔
10 大 HTML 内联 JSON 块不能整块 parse 历史经验 块内出现 ] 会截断切片，导致解析报错 改用纯字符串 replace + 唯一上下文锚定，全程不做整块 parse
11 预览器回写污染交付物 在编辑器里打开 HTML 预览后文件被回写，注入 data-page-node-id 属性 —— 静态报表注入 1,872 处、看板 493 处，体积近乎翻倍（77 KB → 159 KB） 交付前统一剥离该属性，只留洁净副本；并把「交付物洁净度」列为定稿阶段必做项（见 6.5）

05 · Playbook

方法论沉淀Reusable playbook

从这次工作里抽出的 7 条通用做法，适用于任何「多版本数据文件夹 → 可视化交付」的场景。

01
先做内部一致性检查，再谈数字对不对
多版本文件夹里，判断哪份可信的最强手段不是「哪份更新」，而是看哪份自相矛盾。同一实体（小区/城市/门店）被拆到多个类目，就等于该文件有标注错误。
02
口径显式声明，并以编程方式绑定
口径不能靠人记。生成脚本里给不同口径分别命名，正文里所有数字都用变量而不是手写 —— 手写就会出现「图里 46、正文写 39」这种错误。
03
所有数字逐行实算，不引用二手报告
既有报告只用来做交叉核对，绝不用来取数。本次正是靠逐行实算才发现报告整体失真。
04
移动用户文件 = 备份 + 分批 + 字节级校验
顺序固定：整份备份 → 逐文件比对 → 建目录 → 分批移动 → 移动后再比对一次。全程只移动，不删除、不改名、不覆盖。
05
视觉问题用无头截图验证，不靠猜
CSS 改动后必须实际渲染确认。临时视图 + 无头截图的组合，可以在几秒内定位到任意区块并复查修复效果。
06
外部资源先验真，再评估
仓库名、链接、数据来源，先核实存在性。本次 4 个候选里就有 1 个是 404 —— 若不核实，后续所有对比都建立在虚假前提上。
07
交付前必做洁净度与体积复核
文件「能打开、能看」不等于「能交付」。任何在编辑器 / 预览器里打开过的 HTML，都要在定稿前查一遍是否被回写注入了属性、体积是否异常膨胀 —— 这类污染静默发生，肉眼看不出来，但会跟着交付物一起发出去。
